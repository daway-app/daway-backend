# عقد API جلسات المسح بالهاتف — تسليم لتيم فلاتر

> **الغرض:** مرجع واحد مُتحقَّق منه لبناء ميزة «الهاتف كقارئ باركود عن بُعد» في تطبيق فلاتر.
> **المصدر:** الكود الفعلي في `routes/api.php` + `app/Http/Controllers/Api/ScanSessionController.php` + `app/Http/Middleware/AuthorizeScanSession.php` + `app/Support/ScanSessionQr.php`.
> **طريقة التحقق:** `php artisan route:list --path=api/pharmacy/scan-sessions` (**5 مسارات**) + 25 اختبار PHPUnit (114 تأكيد) + الهجرة على MySQL 8.4.8 حقيقيًا.
> **تاريخ التوليد:** 2026-10-16.

## نطاق هذا التسليم

| الطرف | المسؤولية | الحالة |
|---|---|---|
| **Laravel API** | الجلسات الخمس + الأمان + الرموز | ✅ **مكتمل ومختبَر** |
| **تطبيق فلاتر** | مسح الـQR · الاقتران · إرسال الباركود | ⬜ **هذا التسليم** |
| واجهة الويب (React) | **إنشاء** الجلسة و**عرض** رمز الـQR | ⬜ فريق آخر — **لا تنتظره** |

> 🔑 **لا تحتاج واجهة الويب للبدء.** يمكنك إنشاء جلسة بنفسك من الـAPI وقراءة التوكن مباشرة من الاستجابة (§9). الـQR صورة عرض فقط — لا تحتاجها للاختبار.

---

## 1) 🔑 الخبر الجيد: التطبيق لا يحتاج تسجيل دخول

التطبيق **لا يُدخل `pharmacy_id` ولا كلمة مرور**. المستخدم يمسح رمز QR المعروض على شاشة الويب، فيحصل التطبيق على توكن مؤقت صالح لهذه الجلسة وحدها.

```
مسح QR  →  POST pair  →  استلام device_token  →  POST barcode لكل مسح
```

**الثمن المقابل (مقصود):** التوكن مؤقت (5 دقائق افتراضيًا). إن أُغلق التطبيق أو انتهت الجلسة ⇒ مسح QR جديد. لا يوجد مسار «اكتشف جلسة موجودة».

## 2) القواعد العامة

| البند | القيمة |
|---|---|
| **البادئة** | `/api/pharmacy/scan-sessions` |
| **العدد الكلي** | **5 مسارات** |
| **الترويسات** | `Accept: application/json` إلزامية · `Content-Type: application/json` عند وجود جسم |
| **عملة/لغة** | الرسائل **عربية** — اعرِضها كما هي ولا تترجمها |
| **الغلاف** | `{ "success": bool, "message": string, "data": … }` |
| **`data` عند النجاح** | قائمة بيضاء ثابتة (انظر §4.1) |

### 2.1 المصادقة — ثلاث حالات

| المسار | المصادقة |
|---|---|
| `POST /` · `GET /{id}` · `DELETE /{id}` | **Bearer صيدلية** (`auth:sanctum` + `role:pharmacy`) — الويب فقط |
| `POST /{id}/pair` | **`X-Scan-Token`** (من الـQR) **أو** Bearer صيدلية |
| `POST /{id}/barcode` | **`X-Device-Token` وحده** |

### 2.2 رمزان لا رمز واحد — لماذا يهمّك

| الرمز | مصدره | صلاحيته |
|---|---|---|
| `token` (توكن الاقتران) | داخل الـQR — `pairing_url` | **الاقتران فقط.** ⛔ لا يرسل باركودًا |
| `device_token` (توكن الجهاز) | حقل في استجابة `pair` الناجحة | **إرسال الباركود فقط.** ⛔ لا يقترن |

> 🔴 **هذا الفصل ليس تجميلًا.** لو أرسلت الباركود بتوكن الاقتران، لصار الـQR المعروض على الشاشة صلاحية إرسال مفتوحة لكل من يصوّره. الفصل يجعل للـQR قدرة واحدة.

### 2.3 حدّ المعدّل

| المسار | الحدّ | المفتاح |
|---|---|---|
| `POST /` · `DELETE /{id}` | 20/دقيقة | المستخدم |
| `POST /{id}/barcode` | **60/دقيقة** | **الجلسة** (لا الـIP ولا المستخدم) |
| `GET /{id}` | 60/دقيقة | المستخدم (الحدّ العام `api`) |

عند التجاوز: **`429`**. احترم `Retry-After` ولا تُعِد المحاولة فورًا.

## 3) تسلسل الاستدعاء الكامل

```text
[الويب]    POST /api/pharmacy/scan-sessions          (Bearer)
              ↓ 201 + { pairing_url, pairing_qr_svg, pairing_code, seconds_remaining }
           يعرض QR على الشاشة، ويبدأ الاستطلاع كل ثانيتين:
              GET /{id}   (Bearer)

[التطبيق]  يمسح الـQR ⇒ يستخرج sid + token
           POST /{id}/pair  { device_name }   (X-Scan-Token)
              ↓ 200 + { name, platform, device_token }   ← خزّنه
              ↓ 409  ⇒ جهاز آخر مرتبط. أبلِغ المستخدم وانتظر قراره على الويب
              ↓        ثم أعِد POST /pair بعد الموافقة ⇒ 200 + device_token

[التطبيق]  لكل باركود:
           POST /{id}/barcode  { barcode }   (X-Device-Token)
              ↓ 200

[الويب]    الاستطلاع يقرأ `barcode` ⇒ يمرّره إلى محرّك الباركود القائم ⇒ السلة

[الويب]    DELETE /{id}   (Bearer)  ⇒ إغلاق. التوكنان يموتان فورًا.
```

**مهم للتطبيق:** لا تستطلع أنت. الويب هو من يستطلع. التطبيق يرسل فقط.

## 4) نقاط النهاية

### 4.1 `POST /` — إنشاء جلسة (الويب)

**الطلب:** جسم فارغ `{}`.
**الاستجابة:** `201`

```json
{
  "success": true,
  "message": "تم إنشاء جلسة المسح",
  "data": {
    "id": "9c1f0a2e-3b4d-4e5f-8a90-1b2c3d4e5f60",
    "status": "waiting",
    "pairing_code": "A7K92F4B",
    "pairing_url": "daway://pair?sid=9c1f0a2e-…&token=Xk3…",
    "pairing_qr_svg": "<svg xmlns=…>…</svg>",
    "expires_at": "2026-10-16T18:05:00+00:00",
    "seconds_remaining": 300,
    "device": null,
    "devices": [],
    "pending_device": null,
    "barcode": null
  }
}
```

**`data` — قائمة بيضاء ثابتة** (لا حقل غير هذه المفاتيح):

| المفتاح | النوع | ملاحظات |
|---|---|---|
| `id` | string (uuid) | **لا تسلسل** — غير قابل للتعداد |
| `status` | string | `waiting` \| `paired` \| `expired` \| `closed` |
| `pairing_code` | string(8) | رمز عرض بديل للـQR — بلا حروف ملتبسة (0/O/1/I/L) |
| `pairing_url` | string \| null | **يُعاد عند الإنشاء فقط.** يحمل توكن الاقتران |
| `pairing_qr_svg` | string \| null | **يُعاد عند الإنشاء فقط.** SVG جاهز للعرض |
| `expires_at` | ISO8601 | UTC |
| `seconds_remaining` | int | محسوب على **الخادم** — لا تعتمد على ساعة الجهاز |
| `device` | object \| null | `{ name, platform }` — الجهاز النشط |
| `devices` | array | `[{ name, platform, active }]` — عنصر واحد كحد أقصى |
| `pending_device` | object \| null | `{ name }` — جهاز ينتظر قرارًا بشريًّا |
| `barcode` | string \| null | آخر باركود وصل ولم يُستهلك |

> ⚠️ `pairing_url` و`pairing_qr_svg` **`null` في كل استجابة غير الإنشاء** — لا توليد QR في كل استطلاع. لا تعتمد على إعادة قراءتهما.
> ⚠️ `platform` **دائمًا `null`** — العقد لا يحمل نوع المنصّة (انظر §8.1).

### 4.2 `GET /{id}` — حالة الجلسة (الويب)

`{id}` = **uuid**. القيد مفروض في المسار ⇒ أي معرّف غير uuid ⇒ `404`.

**الاستجابة:** `200` بنفس شكل `data` أعلاه (بلا QR).
**`410`** إن انتهت أو أُغلقت — و**تُوسَم الجلسة `expired` في قاعدة البيانات** عند أول قراءة.
**`404`** إن لم تكن الجلسة لهذه الصيدلية (لا نكشف وجودها).

> 🔴 **لا يوجد ETag / `304`.** اعتمد `200` دائمًا واقرأ `data` — أي استجابة بلا جسم تكسر منطق العميل.

### 4.3 `POST /{id}/pair` — اقتران الجهاز

**الترويسة:** `X-Scan-Token: <token>` (من الـQR) — أو Bearer صيدلية (الويب).
**الطلب:**

```json
{ "device_name": "Samsung A52" }
```

`device_name` **اختياري** ≤120 حرف.

**الاستجابة `200`:**

```json
{
  "success": true,
  "message": "تم اقتران الجهاز",
  "data": {
    "name": "Samsung A52",
    "platform": null,
    "device_token": "Qm9…"
  }
}
```

> 🔑 **`device_token` يُعاد مرة واحدة فقط** هنا، ويُخزَّن على الخادم مُهشَّرًا (`sha256`) — لا سبيل لاسترجاعه لاحقًا. **خزّنه في التطبيق.**

**`409` — جهاز آخر مرتبط:**

```json
{ "success": false, "message": "جهاز آخر مرتبط بالجلسة" }
```

لا استيلاء تلقائي. الجهاز الطالب يُسجَّل **طلبًا معلّقًا** يظهر على الويب في `pending_device`، فيقرّر المستخدم [سماح] أو [رفض].
**بعد الموافقة:** أعِد `POST /pair` بالتوكن نفسه ⇒ `200` + `device_token` جديد.

**`401`** توكن خاطئ/مفقود · **`404`** الجلسة ليست لهذه الصيدلية · **`410`** انتهت.

**سلوكيات دقيقة:**

| الحالة | النتيجة |
|---|---|
| جهاز جديد والجلسة فارغة | `200` + `device_token` |
| **نفس** `device_name` أُعيد إرساله | `200` + **`device_token` جديد** (التوكن القديم يموت) — مسار التعافي بعد فقدان التوكن |
| جهاز مختلف والجلسة مشغولة | `409` + تسجيل `pending_device` |
| Bearer صيدلية (موافقة الويب) | `200`، يستبدل الجهاز النشط، **ويمحو `device_token`** ⇒ الجهاز المطرود يفقد قدرته فورًا |

### 4.4 `POST /{id}/barcode` — إرسال باركود

**الترويسة:** `X-Device-Token: <device_token>` — **لا شيء غيرها**.

**الطلب:**

```json
{ "barcode": "6281000123456" }
```

`barcode` **إلزامي** · نصّ · ≤32 حرفًا · لا يكون فارغًا بعد `trim`.

**الاستجابة `200`:**

```json
{ "success": true, "message": "تم استقبال الباركود", "data": { "barcode": "6281000123456" } }
```

| الحالة | الاستجابة |
|---|---|
| نجاح | `200` |
| لا توكن جهاز / توكن خاطئ / استُخدم توكن الاقتران | **`401`** |
| توكن صالح لكن الجلسة ليست `paired` | **`403`** |
| باركود فارغ أو > 32 حرفًا | **`422`** |
| تجاوز 60/دقيقة | **`429`** |
| الجلسة منتهية/مغلقة | **`410`** |

> ⚠️ **الخادم يخزّن نصّ الباركود فقط.** لا بحث عن دواء، لا خصم مخزون، لا إضافة لسلة — الويب هو من يحوّله إلى صنف عبر محرّك الباركود القائم.

### 4.5 `DELETE /{id}` — إغلاق الجلسة (الويب)

**الترويسة:** Bearer صيدلية.
**الاستجابة:** `200` · **`404`** إن لم تكن لهذه الصيدلية.

الإغلاق المتكرّر **نجاح** لا خطأ. بعده: التوكنان ميتان فورًا، وأي `pair`/`barcode` ⇒ `410`.

## 5) جدول الأخطاء

| الكود | متى | ماذا يفعل التطبيق |
|---|---|---|
| **401** | توكن مفقود/خاطئ · استُخدم توكن اقتران لإرسال باركود | **أعد الاقتران**: اطلب مسح QR جديد |
| **403** | توكن جهاز صالح لكن الجلسة ليست `paired` | نادر — أبلِغ واطلب إعادة المسح |
| **404** | الجلسة غير موجودة / ليست لهذه الصيدلية | الجلسة انتهت أو الـQR من صيدلية أخرى ⇒ مسح جديد |
| **409** | جهاز آخر مرتبط | أبلِغ المستخدم بالحرف وانتظر [سماح]، ثم أعِد `pair` |
| **410** | انتهت أو أُغلقت | **اطلب مسح QR جديد** — الحالة الأشيع |
| **422** | باركود فارغ أو أطول من 32 | لا تُعِد المحاولة بنفس المدخل |
| **429** | تجاوز الحدّ | احترم `Retry-After` وتراجع (backoff) |
| **500** | خطأ خادم | خطأ قابل للاسترجاع مع إعادة محاولة واحدة |

## 6) قواعد الأمان (يجب أن يحترمها التطبيق)

1. **لا تُخزّن `pairing_code`** ولا `pairing_url` — استخرج `sid` و`token`، ثم تخلّص من الرابط.
2. **`device_token` يُخزَّن محليًّا بأمان** (Keychain/Keystore) — إنه القدرة الوحيدة للإرسال.
3. **لا ترسل `device_token` إلى أي خادم آخر** ولا تضعه في سجلات (logs).
4. **لا تفترض أن `sid` سرّ** — هو معرّف uuid؛ السرّ هو `token`.
5. **الـQR يحمل جلسة مؤقتة فقط.** لا يحمل كلمة مرور ولا API key ولا `personal_access_token` ولا `pharmacy_id` (مُثبَّت باختبار).
6. **بعد `410`/`409` لا تُعِد المحاولة تلقائيًّا في حلقة** — القرار بشري.

## 7) أمثلة curl

```bash
BASE=https://daway-backend.onrender.com/api
PHARMACY_TOKEN=<sanctum-token>

# 1) الويب: إنشاء جلسة
curl -s -X POST "$BASE/pharmacy/scan-sessions" \
  -H "Accept: application/json" -H "Authorization: Bearer $PHARMACY_TOKEN"

# 2) الويب: استطلاع الحالة (كل ثانيتين)
curl -s -H "Accept: application/json" -H "Authorization: Bearer $PHARMACY_TOKEN" \
  "$BASE/pharmacy/scan-sessions/<SID>"

# 3) التطبيق: اقتران (SID و TOKEN من الـQR)
curl -s -X POST "$BASE/pharmacy/scan-sessions/<SID>/pair" \
  -H "Accept: application/json" -H "Content-Type: application/json" \
  -H "X-Scan-Token: <TOKEN>" \
  -d '{"device_name":"Samsung A52"}'

# 4) التطبيق: إرسال باركود (DEVICE_TOKEN من خطوة 3)
curl -s -X POST "$BASE/pharmacy/scan-sessions/<SID>/barcode" \
  -H "Accept: application/json" -H "Content-Type: application/json" \
  -H "X-Device-Token: <DEVICE_TOKEN>" \
  -d '{"barcode":"6281000123456"}'

# 5) الويب: إغلاق
curl -s -X DELETE "$BASE/pharmacy/scan-sessions/<SID>" \
  -H "Accept: application/json" -H "Authorization: Bearer $PHARMACY_TOKEN"
```

## 8) قيود معروفة (اقرأها قبل البناء)

### 8.1 هوية الجهاز مشتقّة من الاسم
العقد يحمل `device_name` فقط — **لا معرّف جهاز**. لذا يُشتقّ معرّف الجهاز على الخادم من الاسم (`sha1`):
- تطبيق يرسل نفس الاسم دائمًا يُعتبر نفس الجهاز (إعادة اقتران ⇒ `200` + توكن جديد).
- جهازان بنفس الاسم يُعتبران جهازًا واحدًا.
- **التوصية:** أرسل اسمًا ثابتًا وفريدًا لكل جهاز (مثلًا `"Pixel 7 — فرع الرمال"`)، ولا تُغيّره بين الجلسات.

> إن أردت معرّف جهاز حقيقيًّا، فهذا **توسيع عقد** (حقل `device_id` إضافي) يحتاج قرارًا من مالك المشروع — لم يُنفَّذ.

### 8.2 `platform` دائمًا `null`
العقد لا يحمل نوع المنصّة. لا تعتمد على هذا الحقل.

### 8.3 لا مسار «الجلسة النشطة»
المسار الوحيد للدخول هو مسح الـQR. لا يوجد `GET /active`.

### 8.4 عمر الجلسة
**5 دقائق** افتراضيًا (`config('scan_session.session_ttl_minutes')`، قابلة للتغيير بـ`SCAN_SESSION_TTL_MINUTES`). اعتمد `seconds_remaining` من الخادم.

### 8.5 ⚠️ ضغط الاستطلاع
الويب يستطلع كل **2000ms** ⇒ جلسة 5 دقائق ≈ **150 طلبًا**، والحدّ العام `api` = **60/دقيقة لكل مستخدم**. تبويبان مفتوحان على نفس الحساب قد يبلغان الحدّ ⇒ `429`.
**التخفيف الحالي:** `GET /{id}` قراءة صفّ واحد بمفتاح أساسي بلا `joins` ⇒ زمنها زمن الشبكة فقط (وليس 3–12ث كالنقاط الثقيلة).
**تحسينات مؤجَّلة (تحتاج تعديل JS):** رفع الفاصل إلى 3–5ث · long-poll.

## 9) كيف تختبر الآن — بلا انتظار أي واجهة

عرض رمز الـQR مسؤولية واجهة الويب (فريق آخر). **لا تنتظرها**: يمكنك إنشاء جلسة بنفسك وقراءة التوكن مباشرة من الاستجابة. الـQR صورة عرض فقط — وليس قناة بيانات.

### 9.1 احصل على توكن صيدلية

```http
POST /api/login/pharmacy
Content-Type: application/json
Accept: application/json

{ "pharmacy_id": "<pharmacy_custom_id>", "password": "<password>" }
```

```json
{ "success": true, "message": "Logged in successfully",
  "data": { "user": { "id": 12, "name": "صيدلية النور", "pharmacy_id": "PH-0012",
                      "role": "pharmacy", "must_change_password": false },
            "token": "12|Xk3…" } }
```

> `pharmacy_id` هنا = **`pharmacies.pharmacy_custom_id`** (المعرّف المخصّص)، **لا** الـ`id` الرقمي.
> حدود: 5/دقيقة لكل IP و5/دقيقة لكل حساب. الأخطاء: `401` بيانات خاطئة · `403` حساب غير مفعّل (`code: "account_inactive"`).

### 9.2 أنشئ جلسة بنفسك

```bash
curl -s -X POST "$BASE/pharmacy/scan-sessions" \
  -H "Accept: application/json" -H "Authorization: Bearer $TOKEN"
```

### 9.3 اقرأ `sid` و`token` من الاستجابة مباشرة

```json
"pairing_url": "daway://pair?sid=9c1f0a2e-3b4d-4e5f-8a90-1b2c3d4e5f60&token=Xk3…"
```

هذا **نفس المحتوى** الذي سيكون داخل الـQR. استخرجه بتحليل الاستعلام (`query`) — لا بتحليل المسار:

```
sid   = query['sid']
token = query['token']
```

> بهذا يمكنك بناء وتشغيل تدفّق الاقتران كاملًا **قبل** وجود أي واجهة ويب.

### 9.4 لاختبار الكاميرا الحقيقي (اختياري)

الحقل `pairing_qr_svg` في نفس الاستجابة يحوي **SVG جاهزًا**. اعرضه على شاشة أخرى (أو الصق `pairing_url` في أي مولّد QR) ثم امسحه بكاميرا الجهاز — لتتحقّق من مسار `mobile_scanner` الحقيقي لا من الإدخال اليدوي.

### 9.5 تحقّق من نجاح الإرسال

بعد `POST /{id}/barcode` ⇒ `200`، اقرأ `GET /{id}` بـBearer الصيدلية وستجد `barcode` يحمل الرمز المُرسل. هذا يُثبت أن الطرفين يعملان.

## 10) قائمة تحقّق للتطبيق

- [ ] `Accept: application/json` في **كل** طلب.
- [ ] استخراج `sid` و`token` من `pairing_url` ثم **التخلّص من الرابط** (لا تخزّنه).
- [ ] تخزين `device_token` بأمان بعد `pair` ناجح (Keychain / Keystore).
- [ ] إرسال الباركود بـ`X-Device-Token` — **لا** بـ`X-Scan-Token`.
- [ ] التعامل مع `409` بواجهة انتظار + إعادة محاولة **يدوية** (بعد أن يوافق المستخدم على شاشة الويب).
- [ ] `410` ⇒ طلب مسح QR جديد (وليس رسالة خطأ عامة).
- [ ] احترام `Retry-After` عند `429` مع تراجع (backoff).
- [ ] استخدام `seconds_remaining` من الخادم لا ساعة الجهاز.
- [ ] `device_name` ثابت وفريد لكل جهاز (انظر §8.1).
- [ ] عدم إرسال أي توكن إلى سجلات أو خوادم أخرى.
- [ ] إعلان scheme `daway` على المنصّتين ليُفتح التطبيق من الـQR.
- [ ] تحديث نصّ `NSCameraUsageDescription` على iOS ليذكر المسح لا صورة البروفايل.
