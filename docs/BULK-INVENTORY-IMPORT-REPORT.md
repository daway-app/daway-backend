## 1) نطاق العمل

بناء نظام استيراد جماعي للمخزون بواجهتين (Web للصيدلي + API للموبايل) يسمح
برفع ملف Excel/CSV، معاينته بلا أي كتابة، مراجعة كل سطر، ثم تنفيذ مقسّم.

**التدفق المُنفَّذ:** تنزيل القالب → رفع → تحقّق → تحليل → حل الأسماء →
كشف التكرار → Dry-run → معاينة → قرارات المستخدم → Commit مقسّم → تقرير.

## 2) ما فُحص فعلياً قبل الكتابة (PHASE 0)

| ما فُحص | النتيجة المؤثرة في التصميم |
|---|---|
| `pharmacy_medicines` | فيه `unique(pharmacy_id, medicine_id)` ⇒ الـ upsert ممكن وآمن (idempotent) |
| `min_stock` | **مخزَّن ولا يُستخدم فعلياً** — `LowStockNotifier` يستخدم `LOW_STOCK_THRESHOLD` الثابت |
| `MedicineResolver::lookupMapping()` | يمسح ملف 13MB **لكل استعلام** ⇒ 5000 صف = 5000 مسحة |
| `MedicineResolver` | فيه كاش لكل استعلام، لكنه لا يحمي من 5000 استعلام مختلف |
| `LowStockNotifier` | يُطلق FCM **لكل نداء** ⇒ استدعاؤه صفاً صفاً = آلاف الإشعارات |
| `WithHeadingRow` (Maatwebsite) | `HeadingRowFormatter` **حالة عامة قابلة للتغيير** ⇒ خطر تسرّب بين الطلبات |
| قرص `local` في Laravel 13 | جذره `storage/app/private` ⇒ بناء المسار يدوياً يُنتج مساراً خاطئاً |
| `QUEUE_CONNECTION` | `sync` ولا يوجد أي Job/Event ⇒ لا بنية طوابير تُكسَر |
| `LogsExport::safeCell` | سابقة حماية CSV Injection في المشروع ⇒ نتبعها حرفياً |
| `med_medicines_version` | كاش قائمة الأدوية العامة يُبطَل عند إنشاء دواء |
| `bootstrap/app.php` | `writes` = 20/دقيقة بمفتاح `user_id` أو IP |
| `Dockerfile` | يبني الأصول (`npm run build`) وقت النشر ⇒ إضافة ملف CSS آمنة |
| `EnsureRole` / `EnsureProfileComplete` | الصيدلي غير المكتمل يُحوَّل؛ غير الصيدلي يُحوَّل لصفحة الدخول |

**عطل حقيقي اكتُشف أثناء الفحص:** قارئ CSV يخمّن فاصل الأعمدة من أول سطر.
ملف يبدأ بسطر عنوان بلا فواصل (مثل «تقرير مخزون») يجعله يختار فاصلاً خاطئاً،
فينهار التحليل برسالة «لم نتعرّف على صف العناوين» وهي **مضلِّلة**. أُصلح بكشف
الفاصل من محتوى الملف (تفصيل في §17).

## 5) نماذج البيانات والهجرات

**`inventory_imports`** (جديدة)
`id, uuid(unique), pharmacy_id(FK cascade), user_id(FK cascade), original_filename,
file_hash(64), file_path, status(20), total_rows, matched_rows, review_rows,
unmatched_rows, duplicate_rows, error_rows, committed_rows, created_medicines,
rows_payload(longText), commit_summary(longText), committed_at, expires_at, timestamps`
الفهارس: `(pharmacy_id, status)` · `expires_at`.

**`pharmacy_medicine_aliases`** (جديدة)
`id, pharmacy_id(FK), medicine_id(FK), alias(191), timestamps`
`unique(pharmacy_id, alias)` باسم `unique_pharmacy_alias` + فهرس `(pharmacy_id, medicine_id)`.

**لماذا لا Cache لحالة الجلسة:** القرارات نتائج عمل بشري يجب أن تنجو من انتهاء
الجلسة وإعادة التشغيل وإعادة النشر. `Cache` يفقدها بصمت.

**لماذا `uuid` في الروابط:** منع تعداد جلسات الآخرين؛ ويُفلتر إضافةً بذلك
بـ `pharmacy_id` و `user_id`.

## 6) حل الأسماء والمطابقة الحتمية

سلّم واحد، أول قاعدة تنجح تفوز — **لا رقم ثقة مُختلق**:

| # | القاعدة | الحالة |
|---|---|---|
| 1 | مطابقة تامة بالاسم الإنجليزي في الكتالوج المحلي | `EXACT_EN` |
| 2 | مطابقة تامة بالاسم العربي بعد التطبيع | `EXACT_AR_NORMALIZED` |
| 3 | مرادف مؤكَّد سابقاً لهذه الصيدلية | `ALIAS_MATCH` |
| 4 | مطابقة تامة في كتالوج وزارة الصحة | `MOH_MATCH` |
| 5 | مطابقة تقريبية بمرشّح واحد | `FUZZY_MATCH` |
| 5ب | مطابقة تقريبية بأكثر من مرشّح | `REVIEW_REQUIRED` |
| 6 | لا شيء | `UNMATCHED` |
| — | صف غير صالح بنيوياً | `INVALID_ROW` |
| — | أكثر من صف لنفس الدواء | `DUPLICATE` |

**الترتيب مقصود:** المطابقة التامة تتقدّم على المرادف لأنها إشارة موضوعية
لا تعتمد على قرار سابق — نتجنّب تجاوزاً مفاجئاً لدواء موجود فعلاً.

**الحالات 1–3** قابلة للتنفيذ بلا سؤال. **الحالات 4–6 والتكرار** تتطلّب قراراً صريحاً.

### الأداء: من N مسحة إلى مسحة واحدة
`MedicineResolver::lookupMappingBatch()` جديدة — **مسحة واحدة** للملف لكل
الاستعلامات، مع بوّابة `str_contains` رخيصة مثبَت أنها **superset** للمطابق
الأصلي (لا نتائج مفقودة). المنطق نفسه استُخرج إلى `recordMatchesNeedle()`
**حرفياً** لتُعاد استخدامه بلا تكرار — تثبته اختبارات `MedicineResolveTest`
القائمة (28 اختباراً) التي مرّت كما هي.

**حدّان للحماية:** `fuzzy_max_queries` (2000) — ملف كله غير مطابق لا يستحق
مسحاً مكلفاً؛ و`allBucketsFull()` للتوقّف المبكر.

## 7) منع تلويث الكتالوج (الأولوية القصوى)

- **لا إنشاء تلقائي إطلاقاً.** الإنشاء يحتاج `DECISION_CREATE` صريحاً محفوظاً
  على الخادم.
- **المطابقة التقريبية لا تُنشئ شيئاً** — تُنتج اقتراحاً فقط.
- **`moh_id` يجب أن يكون من اقتراحات الصف نفسه** — وإلا رُفض الطلب (422).
  هذا يمنع الواجهة من توجيه الإنشاء لأي عنصر في الكتالوج.
- **`medicine_id` يُعاد التحقق منه** مقابل فهرس حديث من DB — لا نثق بالمعرّف القادم.
- **إعادة التحقق قبل الإنشاء:** `resolveByName(..., lookupMoh: false)` مرة أخرى،
  فقد يكون الدواء أُنشئ بين المعاينة والتنفيذ ⇒ **لا دواء مكرّر**.
- **تأكيد صريح في الواجهة:** عند وجود أدوية جديدة، نافذة تأكيد تذكر العدد بالاسم
  قبل الإرسال.
- **إبطال الكاش:** `MedicineCatalogCache::bump()` يُنادى **فقط** عند
  `created_medicines > 0` — وإلا فالكاش سليم.

## 8) كشف التكرار وقرارات الدمج

- مفتاح المجموعة: `m:{medicine_id}` أو `moh:{moh_id}` أو `in:{اسم مطبّع}`.
- **لا جمع كميات ولا دمج صامت** — الكمية قيمة مطلقة، فجمع صفين لا معنى له.
- **قرار صريح لكل مجموعة:** `keep_last` / `keep_first` / `skip_all`.
- الفائز يُحدَّد حتمياً: `keep_first` ⇒ أصغر رقم سطر، `keep_last` ⇒ أكبره.
- **الخاسر لا يحتاج قراراً فردياً** — قراره محكوم بقرار المجموعة (مثبَّت باختبار).
- المجموعة بلا قرار **تمنع التنفيذ** (لا فائز ⇒ لا كتابة).

**لماذا لا "آخر كتابة تفوز" تلقائياً:** في MySQL بلا `ORDER BY` الترتيب
غير معرَّف، فيصير الناتج عشوائياً — وهو أسوأ من مطالبة المستخدم بقرار.

## 9) Idempotency والـ Commit الذرّي

**الحجز الذرّي** — جملة `UPDATE` واحدة تشمل فحص الحالة وعدم الانتهاء:

```sql
UPDATE inventory_imports
   SET status = 'committed', committed_at = NOW(), updated_at = NOW()
 WHERE id = ? AND pharmacy_id = ?
   AND status IN ('previewed','ready')
   AND (expires_at IS NULL OR expires_at > NOW())
```

`affected_rows == 0` ⇒ رفض «نُفِّذت مسبقاً». **لا فجوة بين الفحص والتنفيذ**،
فالتنفيذ المزدوج مستحيل حتى مع طلبين متزامنين.

**الدفعات:** كل دفعة (`chunk_size` = 500، قابل للضبط) داخل `DB::transaction`
مستقل — لا معاملة واحدة عملاقة تُقفل الجداول وتستهلك الذاكرة.

**عند الفشل:** تُعاد الجلسة إلى `ready`، ويُسجَّل السبب داخلياً، وتُعرض للمستخدم
رسالة عامة بلا تفاصيل داخلية.

**Upsert مقسوم:** الصفوف التي فيها `min_stock` تُكتب معه، والتي لا `min_stock`
فيها **لا تلمسه إطلاقاً** (تفصيل في §14).

## 10) الأداء — لا N+1

| العملية | الاستعلامات |
|---|---|
| بناء الفهرس | **3** ثابتة: `medicines` + `moh_medicines` + `aliases` |
| حل 5000 صف | **0** (كل شيء في الذاكرة) |
| مطابقة تقريبية لملف كامل | **1** مسحة واحدة لملف الـ mapping |
| كتابة 5000 صف | دفعات 500 ⇒ ~10 `upsert` |

`medicines` يُحمَّل كاملاً بمقاطع `chunkById(2000)` (جدول محدود الحجم بطبيعته)،
وهذا يزيل أيضاً **اختلاف حساسية حالة الأحرف** بين MySQL (غير حساس) وSQLite
(حساس) — فتصبح النتيجة واحدة في الإنتاج والاختبار. ويلغي الاعتماد على فهرس
غير موجود على `trade_name_ar`.

الترتيب تصاعدي بالـ `id` مع «أول فوز» ⇒ نفس دلالة `first()` الأصلية.

## 11) الأمان — كل شيء يُعاد التحقق منه على الخادم

| المخاطرة | الإجراء |
|---|---|
| ثقة بـ `medicine_id` من الواجهة | يُتحقّق وجوده في فهرس حديث من DB |
| ثقة بـ `moh_id` من الواجهة | يجب أن يكون من اقتراحات الصف نفسه |
| ثقة بـ `import_id` | يُجلب بـ `uuid` + `pharmacy_id` + `user_id` |
| اسم ملف خبيث / path traversal | اسم مولَّد من الخادم (`uuid.ext`)؛ الاسم الأصلي للعرض فقط بعد إزالة الفواصل |
| امتداد مزيّف | قائمة بيضاء للامتدادات **و** أنواع MIME |
| ملف ضخم | `max_file_kb` (5MB) + `max_rows` (5000) |
| صيغة تُنفَّذ في Excel (CSV Injection) | `safeCell()` مطابق لـ `LogsExport` — `= + - @` تُسبق بـ `'` |
| تفاصيل داخلية في رسائل الخطأ | الفشل يُسجَّل داخلياً، والمستخدم يرى رسالة عامة |
| انتهاء الجلسة | `expires_at` يُفحص في كل عملية **وداخل** جملة الحجز |

**كل قرار يُعاد التحقق منه في `applyDecisions()`** — لا يُقبل شيء كما أرسلته الواجهة.

## 12) الصلاحيات ودورة حياة الجلسة

**دورة الحياة:**
`uploaded → previewed → ready → committed`، ومن `previewed/ready` ⇒ `expired` أو `failed`.

- **الصلاحيات:** `auth` + `role:pharmacy` + `profile.complete`.
- **العزل:** الصيدلية تُستنتج من المستخدم المسجَّل حصراً؛ جلسة صيدلية أخرى ⇒ **404**
  (مثبَّت باختبار ويب واختبار API).
- **الانتهاء:** `session_ttl_hours` (24) افتراضياً، والفحص مزدوج (خدمة + جملة الحجز).
- **لا تنفيذ مزدوج:** الحجز الذرّي (§9).
- **حذف الملف المؤقت** بعد النجاح أو الإلغاء، بلا إفشال العملية لو فشل الحذف.

## 13) حد المعدل

**Limiter جديد `inventory-import`** — منفصل تماماً عن `writes`، ولم يُرفع `writes`.

- **المفتاح = `user_id + pharmacy_id`** (وليس IP): خلف موازن Render يشترك كثير من
  المستخدمين في نفس IP، فمفتاح IP يصبح دلو مشتركاً يحجب أبرياء.
- **السقف:** `rate_limit_per_hour` (10/ساعة) — يرفع السقف للاستيراد دون فتح
  نقاط الكتابة الأخرى للإساءة.
- غير مسجَّل الدخول ⇒ `5/دقيقة` بمفتاح IP.

> ⚠️ **تصحيح بعد بلاغ عبود (HTTP 429):** كان الـ middleware ملفوفاً على **مجموعة
> المسارات كلها** — بما فيها `GET index` و`GET template` — فكان مجرّد *فتح الصفحة*
> يستهلك من الحصة. النتيجة: 11 فتحة صفحة بالساعة = 429 بلا رفع ملف واحد.
> **القاعدة المُصلَحة:** الحد يحرس **الأفعال** (رفع/قرارات/تنفيذ/إلغاء) لا
> تحميل الصفحات ولا التنزيلات. التحليل الكامل والمعالجة في **§20**.

- **مثبَّت باختبارات:** مستخدم ثانٍ من نفس الـ IP لا يتأثر · استهلاك حد الاستيراد
  كاملاً لا يمسّ `writes` · 12 فتحة صفحة لا تستهلك شيئاً من الحصة · 429 يعود
  برسالة عربية و`Retry-After` (ويب) و`retry_after` (JSON).

## 14) `min_stock` — لا كسر صامت

**الواقع المُكتشف:** `min_stock` مخزَّن ولا يُغيِّر حد التنبيه فعلياً —
`LowStockNotifier` يستخدم `PharmacyMedicine::LOW_STOCK_THRESHOLD` الثابت.

**ما نُفِّذ (الخيار الآمن):** يُحفظ `min_stock` كما هو، **ولا ندّعي** أنه يغيّر
التنبيهات. والأهم: الـ upsert **مقسوم** — الصفوف بلا `min_stock` تُكتب في قائمة
منفصلة **لا تتضمّن العمود**، فلا يمحو رفع ملف بلا هذا العمود قيماً موجودة.

**مثبَّت باختبارين:** الغائب يُبقي `7`، والحاضر يحدّثها إلى `4`.

---

## 15) الإشعارات (FCM)

- **لا `LowStockNotifier` لكل صف** — كان سيُنتج آلاف الإشعارات ودفعات FCM.
- **إشعار واحد مجمَّع** بعد نجاح التنفيذ: «تم استيراد مخزونك: N صنف محدَّث،
  وM صنف تحت حد النقص».
- **خارج المعاملة** تماماً.
- **فشل الإشعار لا يُفشل الاستيراد** — `try/catch` يلفّ الإنشاء والإرسال معاً،
  ويُسجَّل تحذير. مثبَّت باختبار يرمي فيه مزوّد الإشعارات استثناءً: الاستيراد
  ينجح والبيانات تُكتب.

## 16) القالب وتقرير الأخطاء

**`InventoryTemplateExport`** — وضعان:
- `empty`: صف عناوين فقط.
- `current`: المخزون الحالي بنفس ترتيب الأعمدة (استعلام واحد مع eager load).

**قرار مقصود:** لا صف مثال داخل الملف — صف مثال يُنسى فيُستورد فعلاً، ونداء
الأخطاء أغلى من ربح توضيحي. الشرح معروض في الواجهة بدلاً منه.

**`InventoryErrorsExport`** — نفس بنية القالب (كي يعدّل الصيدلي ملفه الأصلي
ويعيد رفعه) + أعمدة تشخيص: الحالة، الأخطاء، التحذيرات، الاقتراحات.
**حماية CSV Injection** مطبَّقة على كل خلية نصية — مثبَّتة باختبار يتحقّق أن
`=cmd|calc!A1` تُصدَّر `'=cmd|calc!A1`.

| `import/result` | نتيجة التنفيذ (أسطر محدَّثة/متجاوَزة/أدوية جديدة/مرادفات/نقص) أو رسالة الانتهاء |

**قرارات تصميم الواجهة:**
- **الحالة نص دائماً مع الشارة** — اللون تأكيد إضافي لا القناة الوحيدة للمعنى.
- **RTL بخصائص منطقية** (`inline-start/end`) بلا قواعد مكرّرة.
- **رفع مزدوج ممنوع** — الزر يُعطَّل بعد أول إرسال صالح.
- **قرارات افتراضية مشتقّة من قدرات الصف** (لا من حالة العرض) — لأن صفوف
  التكرار تُعاد كتابة حالتها إلى `DUPLICATE` وتفقد تصنيفها الأصلي.
- **بحث الكتالوج** يعيد استخدام نقطة `pharmacy.medicines.search` القائمة —
  **لا نقطة API جديدة ولا تغيير عقد**.
- **التنفيذ يمر بحفظ القرارات أولاً**: الزر يحفظ (AJAX) ثم يُرسل نموذج التنفيذ؛
  إن فشل الحفظ لا يُنفَّذ شيء.

### الـ API — مسار الموبايل
`GET/POST /api/pharmacy/inventory/import[...]` — **نفس محرّك الويب**، لا منطق
مكرّر ولا اختلاف قواعد. كل النقاط **إضافية بحتة** — لم يُعدَّل أي عقد قائم
(مثبَّت باختبار يتحقّق من شكل `GET /api/pharmacy/inventory` القديم).

### إصلاح قارئ CSV (عطل حقيقي)
`detectDelimiter()` يفحص أول 20 سطراً على البايتات الخام (الفواصل ASCII ⇒ لا
يتأثر بترميز UTF-8 أو Windows-1256) ويختار الفاصل الأكثر **اتساقاً** عبر الأسطر،
ثم يُمرَّر صراحةً للقارئ. المسافة ليست مرشّحاً — واعتبارها كذلك هو تحديداً ما
كان يُفسد ملفات فيها سطر عنوان. الإعداد يُعاد لحالته بعد القراءة.
مثبَّت بأربعة اختبارات (فاصلة منقوطة، سطر عنوان، فاصلة داخل قيمة، والافتراضي).

## 19) القيود المعروفة والخطوات التالية

**قيود مقصودة (مُعلَنة، لا صامتة):**

1. **`min_stock` لا يغيّر حد التنبيه فعلياً** — يُحفظ فقط. تغيير السلوك يحتاج

5. **`medicines` يُحمَّل كاملاً في الذاكرة** — مقبول لكتالوج بحجمه الحالي؛ لو

## 20) تحليل HTTP 429 ومعالجته (بعد بلاغ الإنتاج)

### 20.1 العَرَض

صفحة `429 Too Many Requests` عند استخدام الاستيراد الجماعي — بلا بيان أي حدّ
ضُرب، ولا كم يجب الانتظار، ولا ما العمل.

### 20.2 السبب الجذري (مؤكَّد، لا تخمين)

الـ middleware كان ملفوفاً على **المجموعة كلها**:

```php
// routes/web.php — قبل الإصلاح
Route::middleware('throttle:inventory-import')->group(function () {
    Route::get('/pharmacy/inventory/import', [PharmacyImportController::class, 'index']);   // ← صفحة عادية
    Route::get('/pharmacy/inventory/import/template', [PharmacyImportController::class, 'template']); // ← تنزيل
    Route::post('/pharmacy/inventory/import', [PharmacyImportController::class, 'preview']);
    // ...
});
```

`GET index` **لا يقرأ ملفاً ولا يكتب شيئاً** — مجرّد عرض صفحة. لكنه كان يستهلك
من حصة `10/ساعة`. فالصيدلي الذي فتح الصفحة ويحدّثها ويجول بين التبويبات
يصل إلى 429 **بلا أن يرفع ملفاً واحداً**. هذا هو ما ظهر في اللقطة.

> الدرس: حدّ المعدل يجب أن يحرس **الأفعال**، لا **التصفّح**. خلط الاثنين يحوّل
> الحدّ من حماية إلى عطل.

### 20.3 الأسباب المحتملة لـ429 في هذه المنظومة (تشخيص تفريقي)

429 قد يأتي من خمسة مصادر مختلفة تماماً، ولكل واحد أثر مختلف:

| # | المصدر | العلامة المميّزة | نطاق التأثير |
|---|---|---|---|
| 1 | `throttle:inventory-import` (لنا) | `Retry-After` + `X-RateLimit-Limit: 10` + مسار `/pharmacy/inventory/import*` | الاستيراد فقط |
| 2 | `throttle:api` العام (60/دقيقة) | نفس الترويسات لكن على أي مسار `/api/*` | كل واجهات الموبايل |
| 3 | `throttle:login` / `otp` / `register` (5/دقيقة) | مسارات الدخول والتسجيل فقط | المصادقة |
| 4 | حافة Render / أي CDN أو WAF أمامه | **بلا** `X-RateLimit-*`؛ غالباً `x-render-routing` أو HTML من مزوّد | كل الموقع، وقد يظهر متقطّعاً |
| 5 | مزوّد خارجي (FCM · Cloudinary · كتالوج الوزارة) | لا يظهر للمستخدم كصفحة 429 — يظهر كـ 500 داخلي أو فشل صامت | ميزة واحدة |

**قاعدة الفرز العملية:** وجود `Retry-After` **مع** `X-RateLimit-Limit` ⇒ الحدّ
من داخل التطبيق (1–3)، والمسار يحدّد أيّها. غيابهما مع صفحة HTML غريبة ⇒
المصدر خارجي (4). لا صفحة 429 أصلاً بل خطأ داخلي ⇒ المصدر مزوّد (5).

في حالتنا: المصدر **#1** — والسبب أن الحدّ كان أوسع من اللازم.

### 20.4 المشكلات المرتبطة بحدود المعدل (تصنيف)

1. **حدّ على القراءة بدل الفعل** — يستهلكه التصفّح والتنزيل (سبب هذا البلاغ).
2. **سقف منخفض على عملية ثقيلة** — 10/ساعة معقولة للرفع، لكن لو حُسب عليها
   *فتح الصفحة* يصبح السقف الفعلي «10 تصفّحات» لا «10 عمليات استيراد».
3. **غياب شفافية الحصة** — الصيدلي لا يعرف أنه على وشك الحجب حتى يُحجب.
4. **رسالة حجب بلا مخرج** — «Too Many Attempts» لا تقول كم ينتظر ولا ما العمل.
5. **عميل يعيد المحاولة أعمى** — إعادة الإرسال الفوري على دلو مشترك تُعمّق الحجب.
6. **مفتاح خاطئ (IP)** — خلف موازن Render يصبح الدلو مشتركاً بين مستخدمين أبرياء.
   (هذا كان مُعالَجاً سلفاً بمفتاح `user_id + pharmacy_id` — §13.)
7. **تصادم الحدود** — استهلاك `writes` لحساب الاستيراد يمنع نقاط كتابة أخرى
   لا علاقة لها. (مُعالَج سلفاً بفصل الـ limiter.)

### 20.5 الأثر على معالجة الملف

**أثر على سلامة البيانات: لا شيء — وهذا مقصود ومُتحقَّق منه.**

الـ middleware يعمل **قبل** الـ controller، فطلب محجوب لا يُنشئ `inventory_import`
ولا صفوفاً ولا كتابة جزئية. لا مخزون نصف محدَّث، ولا جلسة معلّقة.

**أثر على التجربة والعمليات:**

- **حلقة إعادة محاولة:** الصيدلي يفسّر 429 كعطل في ملفه فيعيد الرفع، فيستهلك
  حصة أكبر، فيُحجب أسرع. الحدّ يتحوّل من حماية إلى مضاعِف للفشل.
- **التزامن مع الـ PWA:** إعادة المحاولة التلقائية من الـ Service Worker قد
  تضاعف الطلبات بلا علم المستخدم.
- **حجب التنفيذ (`commit`) بعد حفظ القرارات:** أخطر حالة وظيفياً — الصيدلي
  يظن أن المخزون تحدّث وهو لم يتحدّث. **وهذا لا يقع عندنا** لسبب بنيوي:
  `commitBtn` يشغّل `save()` أولاً ولا يُرسل نموذج التنفيذ إلا بعد نجاحه؛ فإن
  حُجب الحفظ توقف المسار كله عند رسالة واضحة. **لا انطباع كاذب بالنجاح.**
- **جلسات شبه ميتة:** رفع نجح ثم حُجب التنفيذ ⇒ جلسة `previewed` تُنتهي
  بـ `expires_at` (24 ساعة) بلا استخدام. تلوّث طفيف لا خطر.
- **أثر على التتبّع:** لو مُسح الـ 429 بإعادة توجيه صامتة بلا تسجيل، يختفي
  الحدّ من المراقبة. (عالجناه بالتسجيل — §20.7.)

### 20.6 المعالجة المطبَّقة

**أ) الفصل: الحدّ على الأفعال لا على الصفحات** — `routes/web.php` و `routes/api.php`

| المسار | قبل | بعد |
|---|---|---|
| `GET index` · `GET template` · `GET show` · `GET errors` | محجوب | **حرّ** (auth + role فقط) |
| `POST preview` · `decide` · `commit` · `cancel` | محجوب | محجوب |

**ب) مصدر واحد للحقيقة** — `app/Support/InventoryImportThrottle.php`

```php
public static function scopeKey(?User $user, ?string $ip = null): string   // المفتاح المنطقي
public static function cacheKey(?User $user, ?string $ip = null): string   // md5('inventory-import'.$key)
public static function used()/remaining()/resetIn()/status()               // للقراءة والعرض
```

سبب وجوده: `ThrottleRequests` **يُجزّئ** المفتاح بـ
`md5($limiterName.$limit->key)` (لأن `$shouldHashKeys = true`)، فمفتاح الكاش
الفعلي ليس النص الذي نمرّره إلى `->by()`. لو حسبت الواجهة المفتاح بنفسها
لانفصلت عن الخادم عند أول تعديل. الآن `bootstrap/app.php` والواجهة يمرّان من
نفس الدالة — فلا يفترق ما نعرضه عمّا يُفرض.

**ج) عرض الحصة المتبقية (وقاية)** — `_rate_limit_note.blade.php`

يظهر فقط **بعد أول فعل فعلي**: «عمليات الاستيراد المتبقية خلال الساعة: 7 من 10».
عند الاستنفاد: تنبيه برتقالي بمدة التجديد. قبل أي فعل: لا شيء — لا ضجيج بصري.

**د) رسالة حجب مفهومة** — `bootstrap/app.php` + مفاتيح i18n جديدة

| نوع الطلب | الاستجابة |
|---|---|
| JSON / Flutter | `429` + `{success:false, message, retry_after}` + ترويسة `Retry-After` |
| نموذج ويب (رفع/تنفيذ/إلغاء) | إعادة توجيه إلى الصفحة نفسها + خطأ عربي في مكان بقية أخطاء الاستيراد |

الرسالة تحمل **عدد الثواني الفعلي** المأخوذ من `Retry-After`، لا نصاً عاماً.

**هـ) تسجيل الحدث** — `Log::warning('inventory import rate limit hit', [...])`
مع `user_id` و`route` و`retry_after`. ضروري لأن مسار الويب يعيد 302 لا 429؛
بلا هذا السجل يختفي الحدّ تماماً من المراقبة.

### 20.7 إعادة المحاولة

المشروع بلا طابور (`QUEUE_CONNECTION=sync`، لا Jobs)، فإعادة المحاولة **متزامنة
على العميل**. المساعد الموحّد في `_rate_limit.blade.php`:

```js
window.DawayRateLimit.request(url, options)   // يقرأ Retry-After، ويعيد المحاولة مرة واحدة
```

| الحالة | السلوك | لماذا |
|---|---|---|
| انتظار ≤ 15 ثانية | انتظار ثم **إعادة محاولة واحدة** | إعادة المحاولة آمنة: 429 تعني أن الطلب رُفض **قبل** الـ controller، فلا ازدواج كتابة |
| انتظار > 15 ثانية | **لا** إعادة محاولة — رسالة بالثواني | تجميد الواجهة دقائق أسوأ من رسالة صريحة |
| الرفع (نموذج ويب) | لا إعادة تلقائية | التنقّل الكامل لا يحتمل، والصيدلي أمامه زر واضح |
| بحث الكتالوج | رسالة داخل قائمة النتائج | كان 429 يظهر سابقاً كـ«لا نتائج مطابقة» — تضليل صريح |
| Flutter | `retry_after` في الجسم | التطبيق يقرّر سياسة الانتظار بنفسه |

**رفضنا** حلقتين: `setInterval` يعيد الإرسال دورياً (يُعمّق الحجب)، وإعادة
محاولة على `commit` بلا سقف (خطر تنفيذ مزدوج لو أُسيء الفهم — الـ
idempotency يحمي، لكن لا نعتمد عليه سلوكياً).

### 20.8 مقايضة مُعلَنة (لا صامتة)

مسار الويب يعيد **302** لا **429**. السبب: الصيدلي أمامه نموذج، والرسالة داخل
الصفحة أنفع له من صفحة خطأ كاملة — وهو نفس نمط بقية أخطاء الاستيراد
(`back()->withErrors()` في `preview()`). المقايضة: يفقد الـ access log دلالة
429 على مسار الويب، **فعوّضناها** بـ `Log::warning` صريح. أما طلبات الـ JSON
(Flutter و`decide`) فتُعيد 429 حقيقياً بترويساته.

- الصفحة تُفتح عادي والحصة صفر، ويظهر «تتجدّد بعد 60 دقيقة».
- مؤشّر الحصة يظهر بعد أول فعل فقط (ولا يظهر قبله).
- استنفاد حصة الاستيراد لا يمسّ `writes` — تحقّق **سلوكي** (نقطة كتابة قديمة
  تعمل) و**رقمي** (`RateLimiter::attempts`).
- **رسم قوالب المراجعة والنتيجة فعلياً** (وهو ما كشف عطلي §20.11).
- صفحة المراجعة تستدعي `DawayRateLimit.request(config.decideUrl…)` — ويُرفض
  أي رجوع إلى `fetch(config.decideUrl…)` خام يتجاهل 429.

**ب) اختبار منطق العميل (بدون متصفح):**

```bash
npm run test:js     # 3 حزم: sw-navigation · sync-reachability · rate-limit-helper
```

`tests/js/rate-limit-helper.test.mjs` (**40 تأكيداً · صفر فشل**) يقرأ المساعد من
**مخرَج Blade الحقيقي** (يرسم القالب بـPHP) ثم يشغّله في `vm` sandbox مع `fetch`
وهمي — فلا يمكن أن يتباعد الاختبار عن الكود:

| الحالة | المُتوقَّع |
|---|---|
| 429 + `Retry-After: 1` | إعادة محاولة واحدة، نجاح، **انتظار 2000ms** بالضبط |
| 429 + `Retry-After: 15` (الحدّ) | **يعيد** المحاولة |
| 429 + `Retry-After: 16` | **لا يعيد** — رسالة بالثواني |
| 429 + `Retry-After: 300` | لا إعادة، لا مؤقّت مُجدول، رسالة تحمل 300 |
| 429 بلا ترويسات | رسالة عامة، `retry_after = 0` |
| `X-RateLimit-Reset` وحده | يُشتق عدد الثواني منه |
| `Retry-After` غير رقمي (HTTP-date) | لا انهيار ⇒ رسالة عامة |
| الحجب مستمرّ بعد الإعادة | **محاولتان لا أكثر** (لا حلقة) |
| 200 | يُقرأ JSON، محاولة واحدة |
| 500 | لا إعادة (429 فقط تُعاد) |

**ج) الحزمة الأوسع:** Web + Api + Admin + Security = **557 نجح · 2443 تأكيد · صفر فشل**.

### 20.10 متابعة اختيارية (بانتظار قرار)

1. **إضافة `rate_limit` إلى payload الـ API** — ليُظهر التطبيق الحصة المتبقية
   مسبقاً. لم نفعله لأنها إضافة على عقد الـ API، وهو قرار مستقل.
2. **صفحة 429 عامة للتطبيق** — حدود الدخول/OTP ما زالت تُظهر صفحة الإطار
   الافتراضية. تحسين مستقل عن الاستيراد.
3. **`errors` و`show` بلا حدّ** — مقصود (قراءة)، لكن تنزيل تقرير أخطاء 5000 صف
   متكرّراً بلا حدّ. لو ظهر إساءة، نضعه على حدّ قراءة خفيف منفصل.
4. **نقل الرفع إلى طابور** — يجعل إعادة المحاولة خادمية بدل عميلية (مؤجَّل بوعي).

### 20.11 عطلان إضافيان كشفهما الاختبار الجديد

كتابة اختبار يرسم صفحة المراجعة فعلياً (لم يكن هناك أي اختبار يفعل ذلك) كشفت
عطلين حقيقيين كانا مخفيين تماماً:

**أ) صفحة المراجعة كانت لا تُفتح إطلاقاً — عطل تركيبي قاتل**

```blade
{{-- قبل --}}
<script id='pi-config' type='application/json'>
    @json([
        'decideUrl' => route(...),   // ← فاصلة
        ...
    ])
</script>
```

توجيه `@json` في Laravel يُنفِّذ `explode(',', $expression)` ويأخذ **الجزء الأول
فقط** (`CompilesJson::compileJson`) — فهو يقبل وسيطة ثانية/ثالثة (flags، depth)
لا أكثر. فأي **فاصلة داخل التعبير** تقصّه بصمت:

```php
// المُخرَج المُصرَّف فعلياً — مصفوفة بلا قوس إغلاق
<?php echo json_encode([
    'decideUrl' => route('...', ['import' => $import->uuid]), 'searchUrl' => route('...')) ?>
```

النتيجة: `PHP parse error: Unclosed '[' on line 414 does not match ')'` ⇒
**صفحة المراجعة 500 دائماً**. لم يُكتشف لأن القالب لم يكن يُرسم في أي اختبار
(الاختبارات كانت تتحقق من إعادة التوجيه فقط، ولا تتبعها).

**الإصلاح:** بناء المصفوفة في `@php` ثم `@json($var)` بلا فواصل. طُبِّق على
`review.blade.php` و`_rate_limit.blade.php` (الأخير كان فيه نفس العطل في سطرين
من ثلاثة). تحقّقنا بمُصرِّف Blade مباشرة: كل قوالب الاستيراد الخمسة تُصرَّف إلى
PHP صالح.

**ب) الجلسة الملغاة كانت تقول «هذه الجلسة نُفِّذت مسبقاً»**

`result.blade.php` كان يقرّر الرسالة بـ `$import->isExpired()`، وهي دالة
**زمنية بحتة** (`expires_at->isPast()`) لا تقرأ الحالة. فجلسة أُلغيَت للتو
(status = `expired`) وحصّتها الزمنية لم تنتهِ بعد كانت تعرض «نُفِّذت مسبقاً» —
**رسالة كاذبة تماماً**: لم يُنفَّذ شيء. صُحِّح ليميّز: فشل التنفيذ ⇒
`error_commit_failed`، وإلا ⇒ `error_expired`. مثبَّت باختبار يتحقق من الظهور
**و** من غياب الرسالة المضلِّلة.

**الدرس المستخلَص:** قالب بلا اختبار يرسمه = كود غير مُختبَر مهما كان عدد
اختبارات المسار. التحقق من «إعادة توجيه 302» لا يقول شيئاً عن الصفحة التي تليها.
