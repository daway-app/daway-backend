## 1) الوضع الحالي — شو موجود فعلاً

| القدرة | الحالة | المرجع |
|---|---|---|
| كتالوج وزارة الصحة | **17,295 دواء** (7.4MB JSON، والنسخة المصنّفة 14MB) | `database/data/moh_medicines.json` |
| مكتبة Excel | **منصّبة أصلاً** `maatwebsite/excel` | `composer.json` |
| سابقة Export | `LogsExport` مع حماية من CSV Injection | `app/Exports/LogsExport.php` |
| سابقة Import | **ما في** — لا يوجد `app/Imports/` | — |
| إضافة دواء واحد | موجودة (ويب + API) | `PharmacyMedicineController::store/storeByName` |
| تحديث **كميات** جماعي | موجود — **للصفوف الموجودة فقط**، بحد **200 عنصر** | `POST /api/inventory/bulk` |
| توحيد حل الأسماء | `resolveByName` (EN → AR → MOH) + إثراء | `MedicineCatalogService` |
| تطبيع الأسماء العربية | `clean()` · `stripDosage()` · `arabicVariants()` · `dropMedialAlif()` | `app/Support/MedicineNameMapper.php` |
| مطابقة ضبابية (fuzzy) | `lookupMapping()` + `normalizeArabic()` + `skeletonOf()` | `app/Services/Ai/MedicineResolver.php` |
| OCR من صورة علبة | موجود (مزوّد خارجي) | `app/Http/Controllers/Api/OcrController.php` |
| باركود | **صفر** — لا عمود ولا جدول ولا بيانات | — |
| مزامنة offline (PWA) | موجودة — طابور حتى 200 عملية | `SyncService`, `public/sw.js` |
| حد الـ rate | `writes` = 20/دقيقة · `register` = 5/دقيقة | `bootstrap/app.php` |

**القيود الحاكمة على أي تصميم:**
- `pharmacy_medicines` فيه **unique على `(pharmacy_id, medicine_id)`** → أي إدخال لازم يكون
  **upsert** وإلا يفشل الصف كامل. هذا **ميزة** — يخلّي إعادة الرفع آمنة (idempotent).
- `pharmacy_medicines` أعمدة: `price` · `quantity` · `is_available` · `min_stock`.
- **ما في Jobs/Queues فعّالة بالمشروع** → المعالجة لازم تكون **متزامنة ومقسّمة لدفعات (chunks)**،
  مش background job، وإلا نكسر نمط المشروع.

## 2) حجم المشكلة بالأرقام

| المؤشر | الرقم | الأثر على التصميم |
|---|---|---|
| كتالوج MOH | 17,295 | البحث بالاسم لازم يكون index-مدعوم، مش full-scan |
| مخزون صيدلية نموذجية | ~500 – 2,000 صنف | ملف إدخال معقول (2,000 صف) |
| سقف Excel | 1,048,576 صف | مش قيد عملي |
| دفعة آمنة للـ insert | 500 صف/transaction | 2,000 صف = 4 دفعات، ثوانٍ معدودة |
| حد `writes` الحالي | 20 طلب/دقيقة | **قيد حرج** — لازم limiter خاص للإدخال الجماعي |

**الخلاصة:** الحجم **مش** المشكلة. المشكلة هي **مطابقة الأسماء** — الصيدلي بيكتب
`Panadol Extra` أو `بنادول اكسترا` أو `panadol xtra`، والكتالوج فيه صيغة واحدة رسمية.
هون بالضبط بيجي دور `MedicineNameMapper` و`MedicineResolver` الموجودين.

## 3) طرق الإدخال — مقارنة وترتيب أولويات

| الطريقة | الجهد التنفيذي | الفائدة الفورية | يغطّي كم % من الصيدليات | القرار |
|---|---|---|---|---|
| **أ) Excel / CSV** | متوسط | ⭐⭐⭐⭐⭐ | ~90% | **المرحلة 1 — الأساس** |
| **ب) الباركود (موبايل)** | متوسط | ⭐⭐⭐⭐ | ~60% | المرحلة 2 |
| **ج) نسخ قالب جاهز (فئات شائعة)** | منخفض | ⭐⭐⭐⭐ | 100% | المرحلة 1 (مرافق) |
| **د) OCR من صورة/فاتورة** | منخفض (موجود) | ⭐⭐ | ~40% | تحسين لاحق |
| **هـ) تكامل مع نظام مخزون/POS** | عالي جداً | ⭐⭐⭐ | <15% | المرحلة 3 (لاحقاً) |

### ليش Excel هو الأساس وليس الباركود؟

1. **كل صيدلية عندها قائمة** — ورقية أو Excel أو تصدير من نظامها. تحويلها لقالب = خطوة وحدة.
2. **مكتبة Excel منصّبة أصلاً** — صفر تبعيات جديدة.
3. **الباركود مش جاهز**: صفر بيانات باركود بالكتالوج. لو بدأنا فيه، الصيدلي بيمسح علبة
   → "غير معروف" → يضطر يكتب الاسم يدوي — يعني ما وفّرنا شي في البداية.
4. **التكامل مع أنظمة المخزون** واقعياً <15% من صيدليات غزة عندها POS. ما يستاهل الاستثمار أولاً.

**ملاحظة مهمة عن "التكامل مع نظام المخزون":** الطريقة الواقعية لهذا السوق هي
**"صدّر من نظامك → ارفع عندنا"**. القالب بيلعب دور الـ integration layer بدون ما نكتب
connector لكل بائع. الـ API/webhook الحقيقي يبقى للسلاسل الكبيرة لاحقاً.

## 4) الحل الموصى به — 3 مراحل

### 🔹 المرحلة 1 — استيراد Excel مع معاينة قبل الحفظ (الأولوية القصوى)

**التدفّق (6 خطوات):**

```
1. تنزيل قالب        →  Excel فيه رأس واضح + Data Validation
2. تعبئة / تصدير     →  من نظام الصيدلية أو يدوياً
3. رفع الملف          →  Upload (ويب + API)
4. معاينة (Dry-run)   →  ✅ مطابق · 🆕 جديد · ⚠️ غامض · ❌ خطأ
5. مراجعة وتصحيح      →  تصحيح الغامض inline
6. تأكيد              →  Chunked upsert + تقرير أخطاء للتنزيل
```

**أعمدة القالب:**

| العمود | إلزامي | ملاحظة |
|---|---|---|
| `trade_name` (EN) | ✅ | الاسم الإنجليزي — مفتاح المطابقة الأساسي |
| `trade_name_ar` | ✖ | يساعد المطابقة لو الإنجليزي ناقص |
| `active_ingredient` | ✅* | إلزامي فقط لو الدواء **جديد** (غير موجود بالكتالوج) |
| `price` | ✅ | رقم ≥ 0 |
| `quantity` | ✅ | عدد صحيح ≥ 0 |
| `barcode` | ✖ | يُقبل الآن، يُستخدم لما نبني الباركود (مستقبلاً) |
| `min_stock` | ✖ | حد التنبيه المنخفض لكل صنف |
| `is_available` | ✖ | افتراضي: `true` |

**منطق المطابقة (بالترتيب — يستخدم الموجود):**
1. `barcode` → (لما يتوفر جدول الباركود)
2. `trade_name` إنجليزي **مطابق تماماً** في `medicines`
3. `trade_name_ar` **مطابق تماماً** بعد `MedicineNameMapper::clean()`
4. مطابقة في **كتالوج MOH** بالاسم الإنجليزي → `findOrCreateFromMoh()`
5. **مطابقة ضبابية** عبر `MedicineResolver::lookupMapping()` (يتعامل مع التشكيل، التطويل، الألف، جرعة الاسم)
6. **فشل** → يُدرج في تقرير "غير مطابق" مع أقرب 3 اقتراحات

**ليه المعاينة (Dry-run) خطوة إلزامية؟**
لأن رفع 2,000 صف بالغلط بيولّد 2,000 سطر ملوّث، وتنظيفه أصعب من منع أصلاً. المعاينة
بتخلّي الصيدلي يشوف **قبل** ما يلمس قاعدة البيانات.

**الملفات المطلوبة:**

| ملف | نوعه | الدور |
|---|---|---|
| `app/Imports/PharmacyInventoryImport.php` | جديد | `ToCollection` + `WithHeadingRow` + `SkipsOnFailure` |
| `app/Exports/InventoryTemplateExport.php` | جديد | توليد القالب (فارغ أو مُعبّأ بالمخزون الحالي) |
| `app/Exports/InventoryErrorsExport.php` | جديد | تقرير الأخطاء (نفس القالب + عمود `error`) |
| `app/Services/InventoryImportService.php` | جديد | المطابقة + المعاينة + الـ upsert المقسّم |
| `app/Http/Controllers/web/Pharmacy/InventoryImportController.php` | جديد | `template()` · `preview()` · `commit()` |
| `app/Http/Controllers/Api/InventoryImportController.php` | جديد | نفس الثلاثة للموبايل |
| `resources/views/pharmacy/inventory/import.blade.php` | جديد | شاشة الرفع + جدول المعاينة |
| `routes/web.php` · `routes/api.php` | تعديل | مسارات جديدة |
| `bootstrap/app.php` | تعديل | limiter جديد `import` (مثلاً 10/ساعة — الملفات ثقيلة) |
| migration | جديدة | `medicine_barcodes` (للباركود مستقبلاً) — أو تُؤجَّل للمرحلة 2 |

**قاعدة `InventoryImportService`:** يستدعي `MedicineCatalogService` الموجود
**بدون تكرار المنطق** — نفس قاعدة H-8 اللي وحّدت الكتالوج سابقاً.

### 🔹 المرحلة 2 — الباركود (موبايل)

**المشكلة الجذرية:** ما في بيانات باركود. الحل **crowd-sourced**:

```sql
medicine_barcodes
  id · medicine_id (FK) · barcode (unique) · source (enum: gs1|moh|crowd)
  confidence (0-100) · verified_by_pharmacy_id · created_at
```

- **many-to-one**: الدواء الواحد بيملك عدة EAN (أحجام علب مختلفة) → الجدول منفصل، مش عمود.
- **التدفّق:** الصيدلي بيمسح → لو معروف: `+quantity` فوراً. لو مجهول: يربطه بالكتالوج **مرة وحدة**
  → يصير معروف للجميع. الكتالوج بيكبر مع كل صيدلية.
- **الواقع:** كتير منتجات محلية/جنيسة بلا EAN → الباركود **مكمّل** للـ Excel، مش بديل.

**الملفات:** عمود `barcode` بالقالب (موجود من المرحلة 1) + endpoint `GET /api/barcodes/{code}`
+ شاشة مسح في تطبيق Flutter.

### 🔹 المرحلة 3 — الفواتير والتكامل (لاحقاً)

- **تحليل فواتير الموزّعين** (Excel/PDF) — أهم من الـ API لأن الموزّعين بيبعتوا فواتير إلكترونية.

## 5) أهم الخطوات لتسريع العملية وتقليل الأخطاء

| # | الأداة/الحل | المشكلة اللي بتحلّها |
|---|---|---|
| 1 | **قالب مُعبّأ مسبقاً** (تنزيل المخزون الحالي للتعديل) | يمنع إعادة كتابة 2,000 صنف من الصفر |
| 2 | **Data Validation بالقالب** (dropdowns، نطاقات رقمية) | يمنع أخطاء الصيغة قبل الرفع |
| 3 | **Dry-run إلزامي** | يمنع تلويث 2,000 صف بالغلط |
| 4 | **Upsert على unique** | إعادة الرفع = تحديث، مش تكرار |
| 5 | **تطبيع عربي + fuzzy** (`MedicineNameMapper` + `MedicineResolver`) | يتعامل مع `بنادول` / `Panadol` / `panadol xtra` |
| 6 | **كشف التكرار داخل الملف نفسه** | نفس الدواء مرتين بالملف |
| 7 | **تقرير أخطاء قابل للتنزيل** (بنفس صيغة القالب) | الصيدلي يصلّح ويعيد الرفع فوراً |
| 8 | **"أضف كل أدوية فئة"** (يستخدم `Category` + `category_medicine_links` الموجودين) | 30 دواء بضغطة بدل 30 سطر |
| 9 | **اقتراح السعر من MOH** (`official_price`) | يقلّل الأخطاء السعرية |
| 10 | **اقتراح أقرب 3 أسماء** عند عدم المطابقة | يحوّل الفشل إلى اختيار بضغطة |
| 11 | **Chunked transaction** (500/دفعة) | أداء ثابت مع الملفات الكبيرة |
| 12 | **صفوف المطابقة المؤكّدة تُحفظ كـ alias** | الرفع الثاني لنفس الصيدلية يصير 100% تلقائي |

**نقطة رقم 12 مهمة:** كل مرة الصيدلي يربط اسم غامض بدواء صحيح، النظام **يتذكّره**.
يعني **المرة الأولى صعبة، والتانية شبه آلية**. هذا أرخص تحسين على المدى الطويل.

## 6) القرار المطلوب منك

الخطة كبيرة — ما رح أبدأ تنفيذ بدون موافقتك على النطاق. الخيارات:

- **أ)** ابدأ **المرحلة 1 كاملة** (Excel: قالب + معاينة + تأكيد + تقرير أخطاء) — الويب أولاً.
- **ب)** ابدأ **شريحة صغيرة** من المرحلة 1: قالب + رفع + مطابقة + حفظ (بدون شاشة معاينة)
  → أسرع للتجربة، ونضيف المعاينة بعدها.
- **ج)** ابدأ بالـ **API فقط** (للموبايل) لأن الصيدلي غالباً على الموبايل.
- **د)** تعديل/إعادة ترتيب الأولويات.

**توصيتي:** **(ب)** — شريحة رأسية كاملة تعمل من البداية للنهاية على الويب، نجرّبها على
ملف حقيقي، وبعدها نضيف المعاينة والـ API. أقل مخاطرة، وأسرع تعلّم من ملف فعلي.

## 7) مخاطر وتنبيهات

- **حد الـ rate `writes` (20/دقيقة)** ما يكفي لرفع ملف — لازم limiter منفصل، وإلا الصيدلي ينحظر.
- **`maatwebsite/excel` على Render المجاني**: الملفات الكبيرة تستهلك ذاكرة. لازم `chunk_reading`
  وسقف حجم ملف (مثلاً 5MB / 5,000 صف).
- **ما في Queue فعّالة** → المعالجة متزامنة؛ ملف 5,000 صف ممكن يلمس `max_execution_time`.
  الحل: `set_time_limit(0)` (نفس نمط `CatalogImportController` الموجود) + تقسيم.
- **عدم تغيير عقد الـ API**: أي endpoint جديد يكون **إضافي**، بدون لمس
  `availability` / `inquiry` / `notifications`.
- **تلويث الكتالوج العام**: استيراد جماعي بأسماء حرّة ممكن يولّد مئات الأدوية المكرّرة
  في `medicines`. لازم **عتبة ثقة**: صف بدون مطابقة **واضحة** ما يُنشئ دواء جديد تلقائياً
  إلا بموافقة صريحة من الصيدلي في شاشة المعاينة.
